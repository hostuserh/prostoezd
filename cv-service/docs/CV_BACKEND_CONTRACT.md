# Контракт CV-сервис → Backend (ParkVision)

**Кому:** GPT Astra (backend, FastAPI + PostgreSQL/PostGIS)
**От кого:** A5, CV-сервис, слой доставки статусов (`cv-service/cvsvc/publish/`)
**База:** `CLAUDE.md` в корне репозитория — источник правды по контракту
**Статус:** предложение CV-стороны, уже реализованное и покрытое тестами
**Дата:** 13 ноября 2026

Документ самодостаточен: чтобы реализовать приёмную сторону, читать код
CV-сервиса не нужно. Весь контракт описан здесь, а исполняемая спецификация —
в `cv-service/tests/mock_backend.py` (рабочий FastAPI-мок, который можно
поднять и потыкать, см. раздел 11).

## 1. Что мы шлём и с какой частотой

Три камеры: `CAM-001` (кольцо Багратиона, 1920×1080), `CAM-002` (центр,
1920×1080), `CAM-003` (ТЦ Снеговая падь, 2592×1944).

CV-цикл синхронный, камеры обрабатываются последовательно. Раз в
`FRAME_INTERVAL` (по умолчанию 15 с) по каждой камере уходит **один POST с
полным снапшотом** состояния всех её объектов — не дельта.

> **Почему полный снапшот, а не дельта.** Мест на камеру — десятки, payload
> ~2–6 КБ, это дёшево. Зато у backend всегда свежий `updated_at` по каждому
> месту, и потеря одного POST не оставляет место «подвисшим» в старом статусе
> навсегда. Критерий MVP «устаревшие статусы не показываются как free»
> работает только если `updated_at` обновляется на КАЖДОМ цикле.

Нагрузка: 3 камеры / 15 с ≈ **0.2 запроса в секунду**. Планировать под это.

## 2. Транспорт и аутентификация

```
POST {BACKEND_URL}/api/v1/internal/occupancy
Content-Type: application/json
Authorization: Bearer {CV_SERVICE_TOKEN}
```

- `BACKEND_URL` и `CV_SERVICE_TOKEN` — переменные окружения из `CLAUDE.md`
  (в docker-compose это `http://backend:8000` и общий секрет).
- Токен сравнивается строкой целиком. Просьба: при несовпадении возвращать
  **401**, а не 403 и не 200 — мы на 401 не ретраим, а сразу шумим в лог.
- Таймаут на нашей стороне — **5 секунд** на запрос. Если ваш обработчик
  может работать дольше, скажите, подниму.

## 3. Payload `POST /internal/occupancy`

### 3.1. Минимальный payload — ровно как в `CLAUDE.md`

Этот payload обязан остаться валидным навсегда. Все наши расширения —
строго additive, с умолчаниями.

```json
{
  "camera_id": "CAM-001",
  "timestamp": "2026-11-13T10:30:00+10:00",
  "detections": [
    {"spot_id": "S-014", "status": "free", "confidence": 0.97},
    {"spot_id": "S-015", "status": "occupied", "confidence": 0.99}
  ]
}
```

### 3.2. Расширенный payload — то, что мы шлём на самом деле

```json
{
  "camera_id": "CAM-003",
  "timestamp": "2026-11-13T10:30:00+10:00",
  "frame_id": "CAM-003-1794539345",
  "camera_status": "active",
  "detections": [
    {"spot_id": "S-301", "status": "free", "confidence": 0.97}
  ],
  "zone_counts": [
    {"zone_id": "Z-301", "capacity": 42, "free": 7, "occupied": 33, "unknown": 2, "confidence": 0.88}
  ]
}
```

### 3.3. Поля

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `camera_id` | string | да | `CAM-001` / `CAM-002` / `CAM-003` |
| `timestamp` | string, ISO-8601 **с таймзоной** | да | Время **кадра** (см. §4.9). Всегда `+10:00` |
| `detections` | array | нет* | Дискретные места. Может быть `[]` или отсутствовать, если камера смотрит только на зоны |
| `detections[].spot_id` | string | да | `S-xxx`, совпадает с `ParkingSpot.id` из сид-файла |
| `detections[].status` | enum | да | `free` \| `occupied` \| **`unknown`** (см. §4.8) |
| `detections[].confidence` | float `0.0..1.0` | да | Уверенность модели |
| `frame_id` | string | нет (EXT) | `"{camera_id}-{unix_ts_кадра}"`. Ключ дедупликации (§4.6) |
| `camera_status` | enum | нет (EXT) | `active` \| `inactive` \| `error` — здоровье камеры (§4.4) |
| `zone_counts` | array | нет (EXT) | Агрегаты по зонам без разметки мест (§4.1) |
| `zone_counts[].zone_id` | string | да в объекте | `Z-xxx` |
| `zone_counts[].capacity` | int ≥ 0 | да в объекте | Вместимость зоны по нашей разметке |
| `zone_counts[].free` / `.occupied` / `.unknown` | int ≥ 0 | да в объекте | **Инвариант: `free + occupied + unknown == capacity`** |
| `zone_counts[].confidence` | float `0.0..1.0` | да в объекте | Средняя уверенность по зоне |

\* Формально обязательны только `camera_id` и `timestamp`. Но хотя бы один из
`detections` / `zone_counts` должен быть непустым — пустой снапшот мы не
отправляем, и вам его тоже стоит отклонять (422).

Гарантии с нашей стороны:
- `spot_id` внутри одного payload не повторяются, `zone_id` тоже;
- `detections` — **полный** список мест камеры, не подмножество;
- если место не распознано, мы шлём его со статусом `unknown`, а не выкидываем
  из списка;
- детекции с `confidence < CONFIDENCE_THRESHOLD` (по умолчанию 0.7) мы сами
  понижаем до `unknown`, сохраняя исходное значение `confidence`. То есть
  `status: "free", confidence: 0.4` вы от нас не увидите.

**Просьба:** неизвестные поля в payload **игнорировать**, а не возвращать 422.
Это даст нам возможность добавлять поля, не ломая вас (и наоборот).

### 3.4. JSON Schema

Схему можно сгенерировать из наших моделей одной командой (без запуска сервиса):

```bash
cd cv-service
python -c "import json, sys; sys.path.insert(0,'.'); \
from cvsvc.publish.schemas import OccupancyPayload; \
print(json.dumps(OccupancyPayload.model_json_schema(), ensure_ascii=False, indent=2))"
```

## 4. Десять пробелов спеки и наши предложения

### 4.1. Зон в спеке нет вообще

**Как есть.** `CLAUDE.md` знает только `ParkingSpot` — дискретное место с
собственным `id`, координатами и `roi_polygon`.

**Проблема.** Разметка у нас **гибридная**. Там, где на асфальте есть краска,
места действительно дискретные. Но большинство площадок на наших трёх камерах —
грунтовые/хаотичные карманы без разметки. Нарезать там «места» значит выдумать
`S-xxx`, которых физически не существует: машины встают как попало, границы
«мест» поедут на первом же кадре, а пользователю мы покажем точку, на которой
никакого места нет. Это прямо противоречит критерию «Пользователь может выбрать
конкретное место по ID».

**Предложение.** Ввести второй тип объекта — **зону**:

> Зона = полигон + `capacity` + счётчики занятых/свободных, **без
> индивидуальных ID мест**.

В БД для этого **не нужна новая таблица**: зона ложится на существующий
`ParkingLot`, у которого просто нет связанных `ParkingSpot`. В `GET /parkings`
уже есть ровно те поля, что нам нужны: `capacity`, `free_spots`,
`occupied_spots`, `unknown_spots`. Нужно только:

1. добавить `ParkingLot.has_discrete_spots: bool` (default `true` —
   обратносовместимо) и `ParkingLot.zone_id: string | null`;
2. при приёме `zone_counts[]` писать счётчики прямо в парковку с
   соответствующим `zone_id`, а не в места.

Последствия для остального API (и это надо решить до интеграции):

- `GET /parkings/{id}/spots` для зоны возвращает `{"spots": []}` — не 404.
- `POST /recommendations` для зоны отдаёт рекомендацию **уровня парковки**:
  `spot_id` = `null`, а `location`/`approach_point` = точка подъезда зоны.
  Мобильному клиенту (A3) надо будет это обработать: для зоны показываем
  «свободно ~7 из 42», а не конкретное место на схеме.
  **Альтернатива, если `spot_id: null` вам неудобен:** `spot_id` = `zone_id`
  (`"Z-301"`) плюс флаг `"is_zone": true`. Мне вариант с `null` нравится
  меньше — выбирайте вы, это ваша модель ответа.
- История: `OccupancyHistory` для зоны пишется агрегатом. Предлагаю добавить
  `OccupancyHistory.zone_id` (nullable) рядом с `spot_id` и сохранять
  `free`/`occupied`/`unknown`. Без этого XGBoost из P2 потом не на чем учить.

### 4.2. Кто создаёт места в БД?

**Как есть.** Ни в одном эндпоинте нет регистрации мест. CV-сервис знает
`roi_polygon` и координаты, backend — нет, и эндпоинта «вот мои места» не
существует. Если мы начнём слать детекции по `S-014`, которого нет в БД,
получится мусор или 400 на каждый цикл.

**Предложение.** Мы отдаём файл **`cv-service/seed/spots.json`** — полностью по
модели `ParkingSpot` из `CLAUDE.md` (плюс `roi_frame_size`, см. §4.5), а вы
заливаете его сидом/миграцией при старте. Файл в репозитории, обновляется нами
по мере разметки; после каждого обновления нужен ре-сид.

Формат файла:

```json
{
  "version": 3,
  "generated_at": "2026-11-13T09:00:00+10:00",
  "parking_lots": [
    {
      "id": "P-001",
      "name": "Парковка у ТЦ Снеговая падь",
      "latitude": 43.166500,
      "longitude": 132.000100,
      "capacity": 42,
      "parking_type": "free",
      "access_rules": "круглосуточно",
      "entrance_lat": 43.166620,
      "entrance_lon": 132.000240,
      "has_discrete_spots": false,
      "zone_id": "Z-301"
    }
  ],
  "cameras": [
    {
      "id": "CAM-003",
      "parking_lot_id": "P-001",
      "source_reference": "<HLS url, в репозиторий не кладём>",
      "status": "active",
      "frame_size": [2592, 1944]
    }
  ],
  "spots": [
    {
      "id": "S-301",
      "parking_lot_id": "P-001",
      "camera_id": "CAM-003",
      "latitude": 43.166510,
      "longitude": 132.000080,
      "approach_lat": 43.166620,
      "approach_lon": 132.000240,
      "roi_polygon": [[1040, 880], [1190, 880], [1190, 1010], [1040, 1010]],
      "roi_frame_size": [2592, 1944],
      "spot_type": "standard",
      "status": "unknown",
      "confidence": 0.0,
      "updated_at": "2026-11-13T09:00:00+10:00"
    }
  ]
}
```

Замечания:
- `roi_polygon` вам не нужен для работы API — он нужен админке (P1) и как
  единственное место, где разметка хранится версионно. Складывайте в `JSONB`.
- `source_reference` камеры — секрет, в сиде его не будет (пустая строка или
  плейсхолдер). Реальный URL живёт в `.env` CV-сервиса. В `CLAUDE.md` это
  прямо записано в принципах безопасности.
- Начальный `status` всех мест — `unknown`, а не `free`. Пока не пришёл первый
  снапшот, показывать место свободным нельзя.

**Что нужно от вас:** подтвердить формат и то, что ре-сид идемпотентен
(upsert по `id`, а не «упасть на дубликате»). Если вам удобнее эндпоинт
`POST /internal/spots/bulk` вместо файла — скажите, сделаем, но на 48 часов
сид-файл дешевле.

### 4.3. Нет эндпоинта конфигурации камер

**Как есть.** Псевдокод CV-пайплайна в `CLAUDE.md` вызывает
`get_camera_config(camera_id)` («Получить настройки камеры из БД (ROI для
каждого места)»), но такого эндпоинта в API нет.

**Решение на MVP.** Источник правды по конфигам камер и ROI — **наш файл
`cv-service/config/cameras.yml`**. Из БД мы конфиг не читаем, обращений к вам
на этом пути нет. Это снимает зависимость и убирает лишний round-trip в
горячем цикле.

**Что понадобится позже (P1, админка).** Когда появится разметка ROI через
Streamlit, источник правды должен переехать в БД, и тогда нужен:

```
GET /api/v1/internal/cameras/{camera_id}/config
Authorization: Bearer {CV_SERVICE_TOKEN}
```
```json
{
  "camera_id": "CAM-003",
  "frame_size": [2592, 1944],
  "config_version": 7,
  "spots": [
    {"spot_id": "S-301", "roi_polygon": [[1040,880],[1190,880],[1190,1010],[1040,1010]]}
  ],
  "zones": [
    {"zone_id": "Z-301", "capacity": 42, "roi_polygon": [[100,700],[2400,700],[2400,1900],[100,1900]]}
  ]
}
```

Ключевое поле — `config_version`: мы опрашиваем конфиг редко (раз в минуту) и
перечитываем разметку, только если версия изменилась. **Делать этот эндпоинт
сейчас не нужно**, но заложите `config_version` в схему таблиц, иначе потом
переделывать.

### 4.4. Нет способа сообщить о здоровье камеры

**Как есть.** В модели `Camera` есть `status` (`active|inactive|error`) и
`last_frame_at`, но ни один эндпоинт их не обновляет. Поля мёртвые.

**Проблема.** Если камера отвалилась, backend об этом не узнает: снапшоты
просто перестанут приходить, и места останутся с последним известным статусом.
Критерий MVP «устаревшие статусы не показываются как free» вы сможете
выполнить только по `updated_at`, вслепую, без понимания причины.

**Предложение — ничего нового не изобретать, добавить два поля в тот же
payload:**

- `camera_status` — `active` / `inactive` / `error`;
- `frame_id` — идентификатор кадра.

При приёме снапшота вы обновляете `Camera.status = camera_status` и
`Camera.last_frame_at = timestamp`. Никаких дополнительных эндпоинтов.

Отдельный случай: камера недоступна, кадра нет. Тогда мы шлём
**heartbeat-снапшот** — все её места со статусом `unknown`, `confidence: 0.0`,
`camera_status: "error"`, `timestamp` = время попытки:

```json
{
  "camera_id": "CAM-002",
  "timestamp": "2026-11-13T10:31:00+10:00",
  "frame_id": "CAM-002-1794539460",
  "camera_status": "error",
  "detections": [
    {"spot_id": "S-201", "status": "unknown", "confidence": 0.0},
    {"spot_id": "S-202", "status": "unknown", "confidence": 0.0}
  ]
}
```

Так места честно гаснут в `unknown` вместо того, чтобы протухать во `free`.

### 4.5. У `roi_polygon` нет привязки к разрешению кадра

**Как есть.** `ParkingSpot.roi_polygon` — список точек в пикселях кадра, но
нигде не записано, **какого именно кадра**.

**Проблема конкретная, не теоретическая.** У нас `CAM-001`/`CAM-002` —
1920×1080, `CAM-003` — 2592×1944. Если поток переключит профиль (а HLS это
делает сам, при смене битрейта), полигон, размеченный на 2592×1944,
молча «съедет» на кадре 1920×1080 — ошибки не будет, просто вся разметка
начнёт показывать не те куски асфальта. Отладить это потом на хакатоне нереально.

**Предложение.** Добавить в `ParkingSpot` обязательное поле:

```json
"roi_frame_size": [2592, 1944]
```

и в `Camera` — необязательное `frame_size: [w, h]` (текущее разрешение потока).
Валидация на нашей стороне уже есть: ROI вне границ кадра — ошибка схемы.
От вас нужно только сохранить поле и отдавать его в конфиге камеры (§4.3),
когда он появится. Миграция: тип `integer[2]` / `JSONB`, nullable не надо —
для существующих мест проставьте разрешение их камеры.

### 4.6. Идемпотентность и ретраи не описаны

**Как есть.** В спеке нет ни слова о том, что делать с повторной доставкой.

**Что делаем мы.** На 5xx, 429 и сетевых ошибках — **до 3 попыток** с
экспоненциальным бэкоффом и джиттером. Значит, backend **гарантированно
увидит один и тот же снапшот дважды**: классический случай — вы приняли и
записали, но ответ не доехал (таймаут на нашей стороне), мы ретраим.

Плюс при недоступности backend снапшоты копятся у нас в SQLite-буфере и
дозаливаются после подъёма — пачкой, **строго в порядке `timestamp` кадра**.
То есть после пятиминутной аварии вам прилетит ~60 снапшотов подряд, по
возрастанию времени.

**Что нужно от вас:**

1. **Дедуп по `frame_id`.** Храните принятые `frame_id` (хотя бы за последний
   час) и на повтор отвечайте `200` с `"duplicate": true`, не применяя
   изменения второй раз.
2. **Не регрессировать по времени.** При записи статуса применяйте
   `UPDATE ... WHERE updated_at < :timestamp` (или `GREATEST`). Это
   страхует на случай, если из-за ретрая порядок всё-таки нарушится: более
   старый снапшот не должен затирать более свежий.
3. **Пережить всплеск** в ~60 запросов подряд после аварии без 429. Если
   429 всё же будет — мы его ретраим как 5xx, это нормально, но честнее
   просто принять.

Если `frame_id` вам хранить не хочется, пункта 2 по-хорошему хватает:
применение снапшота идемпотентно по смыслу (мы шлём полное состояние, а не
инкремент). Тогда просто отвечайте `200` и на повтор — мы это разберём.
**Подтвердите, какой вариант выбираете.**

### 4.7. Что делать с неизвестным `spot_id`

**Как есть.** Не описано. Варианты: 400 на весь батч или частичный приём.

**Почему это важно.** Рассинхрон сид-файла и нашей разметки неизбежен: мы
размечаем новое место, а ре-сид ещё не прокатили. Если вы на один незнакомый
`spot_id` вернёте 400 на весь батч, то **вся камера перестанет обновляться** —
из-за одного места потеряем десятки. Это худший из возможных режимов отказа.

**Просьба: частичный приём.** Принять всё, что знаете, и перечислить
отклонённое в ответе:

```json
{
  "status": "partially_accepted",
  "processed": 11,
  "timestamp": "2026-11-13T10:30:01+10:00",
  "rejected": [
    {"spot_id": "S-399", "reason": "unknown_spot_id"}
  ]
}
```

HTTP-код — **200** (не 207, не 400). Мы считаем такой ответ успешной
доставкой, не ретраим, но пишем `WARNING` со списком отклонённых — это сигнал
«пора ре-сидить». `reason` — свободная строка, мы её только логируем.

400 оставьте для действительно битого запроса: невалидный JSON, отсутствующий
`camera_id`, неизвестный `camera_id`. Такое мы не ретраим и уводим в DLQ.

### 4.8. Принимает ли backend `status: "unknown"`?

**Как есть.** В модели `ParkingSpot` значение `unknown` есть и описано в
разделе «Обработка ошибок CV». А в примере запроса `POST /internal/occupancy`
встречаются только `free` и `occupied`. Если вы сделаете enum по примеру,
`unknown` отвалится с 422.

**Мы шлём `unknown`, и это важно.** Он выставляется при `confidence < 0.7`,
перекрытии обзора, плохом освещении (а зимой во Владивостоке в 17:00 темно),
недоступности камеры. Это прямое требование `CLAUDE.md`: «Явная обработка
неопределённости» в принципах архитектуры и критерий P0 «Устаревшие/
неопределённые статусы не показываются как `free`».

**Просьба:** принимать `free | occupied | unknown` в `detections[].status`,
`unknown` хранить как есть, в `GET /parkings` считать в `unknown_spots`, а в
`POST /recommendations` — **фильтровать** (по алгоритму из `CLAUDE.md`:
«Исключить места со статусом `occupied` или `unknown`»).
**Подтвердите, что enum включает `unknown`.**

### 4.9. `timestamp` — время кадра или время отправки?

**Мы шлём время КАДРА.** Момент, когда кадр снят (точнее — когда получен из
потока), а не момент HTTP-запроса. Разница в норме доли секунды, но при
дозаливке из буфера после аварии она достигает **минут**: снапшот с
`timestamp: 10:30:00` может приехать в 10:35:00. Это ожидаемо и правильно.

Следствия для вас:
- `ParkingSpot.updated_at` ставьте **из `timestamp` payload**, не из `now()`.
  Иначе после дозаливки все места разом получат свежий `updated_at`, и логика
  «данные старше 60 секунд → не показывать как free» из алгоритма рекомендаций
  молча сломается — покажем пользователю пятиминутной давности «свободно».
- `OccupancyHistory.observed_at` — тоже из `timestamp`.
- `timestamp` в вашем **ответе** — ваше серверное время, нам всё равно.
- Все метки — timezone-aware, `+10:00` (Владивосток, без перехода на летнее
  время). Naive datetime мы не отправляем, и вам советую отклонять такие 422.

### 4.10. Координаты в примерах спеки — заглушка

**Как есть.** Во всех примерах `CLAUDE.md` фигурируют `43.115141, 131.885341`
(ТЦ Clover House, `P-001`).

**Факт:** к нашим трём камерам это отношения не имеет. Пилот — кольцо
Багратиона, центр и ТЦ Снеговая падь. Не хардкодьте эти координаты в сиды,
фикстуры, дефолты карты или тесты: они разъедутся с реальностью на демо.

**Кто ставит реальные координаты.** Мы. Привязка «пиксель на кадре → lat/lon»
делается при разметке ROI, вручную по спутниковому снимку, и попадает в
`seed/spots.json` (§4.2). Оттуда же берутся `approach_lat`/`approach_lon` —
точка подъезда, к которой 2ГИС строит маршрут; она отличается от координаты
самого места (машину надо подвезти ко въезду в карман, а не в середину ряда).

**Что нужно от вас:** брать координаты строго из сид-файла, своих значений не
придумывать и не «уточнять» их геокодером. И передайте A3 (Flutter), чтобы
начальный центр карты тоже брался из `GET /parkings`, а не из константы.

## 5. Ответ `POST /internal/occupancy`

### 5.1. Успех — как в `CLAUDE.md`

```json
{
  "status": "accepted",
  "processed": 2,
  "timestamp": "2026-11-13T10:30:01+10:00"
}
```

### 5.2. Полная схема ответа

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `status` | string | да | `accepted` / `partially_accepted` |
| `processed` | int ≥ 0 | да | Сколько объектов применено (места + зоны) |
| `timestamp` | ISO-8601 с TZ | да | Серверное время приёма |
| `rejected` | array | нет (EXT) | `[{"spot_id": "...", "reason": "..."}]`, см. §4.7 |
| `duplicate` | bool | нет (EXT) | `true`, если снапшот с таким `frame_id` уже принят (§4.6) |

Отсутствующие `rejected` / `duplicate` трактуем как `[]` / `false` — то есть
ответ из спеки работает без изменений.

---

## 6. Коды ответов и наша реакция

| Код | Что это значит | Что делает CV-сервис |
|---|---|---|
| `200` / `2xx` | Принято (в т.ч. частично или как дубль) | Успех. `rejected` → WARNING в лог |
| `400` | Битый запрос, неизвестный `camera_id` | **Не ретраим.** В DLQ + ERROR |
| `401` / `403` | Плохой или отсутствующий токен | **Не ретраим.** В DLQ + ERROR. Чиним конфиг руками |
| `404` | Неверный путь | **Не ретраим.** В DLQ + ERROR |
| `422` | Payload не прошёл вашу валидацию | **Не ретраим.** В DLQ + ERROR. Означает расхождение схем — чиним контракт |
| `429` | Rate limit | Ретраим как 5xx |
| `5xx` | Ваша авария | 3 попытки с бэкоффом, затем в буфер и дозаливка |
| таймаут / нет соединения | Backend лежит или недоступен | То же: 3 попытки, затем буфер |

**Важно:** 4xx (кроме 429) означает, что снапшот потерян навсегда — он уходит в
dead-letter-очередь и не ретраится. Поэтому не отвечайте 4xx на временные
проблемы (например, «БД ещё не прогрелась» — это 503, а не 400).

**Про поведение при дозаливке:** если во время дозаливки буфера какой-то
снапшот получает 4xx, мы убираем его в DLQ и **продолжаем** с остальными —
одна битая запись не должна навсегда заблокировать очередь.

## 7. Буферизация на нашей стороне (чтобы вы знали, чего ждать)

- Буфер — SQLite-файл `buffer.db`, переживает рестарт CV-сервиса.
- Глубина — **2000 снапшотов** (≈ 2.7 часа аварии при 3 камерах / 15 с).
  При переполнении вытесняются **самые старые**: свежие статусы ценнее.
- Дозаливка идёт **строго по возрастанию `timestamp` кадра** и
  останавливается на первой неудаче — чтобы вы никогда не увидели более свежий
  снапшот раньше более старого.
- Публикация ограничена бюджетом времени (по умолчанию = `FRAME_INTERVAL`),
  чтобы доставка не тормозила CV-цикл. Если бюджет исчерпан, остаток уедет
  на следующем цикле.
- Токен в логи не попадает ни в каком виде — только маска `<len=N:…xxxx>`.

Практический вывод для вас: **после вашего рестарта будет всплеск.** Если вы
поднимаетесь раньше, чем прогрелась БД, — отвечайте `503`, а не `500` с
тем же эффектом, и уж точно не `400`.

## 8. `GET /health`

Мы используем его для диагностики (и для readiness в docker-compose), в
горячем цикле не дёргаем.

```json
{
  "status": "healthy",
  "version": "1.0.0",
  "timestamp": "2026-11-13T10:30:00+10:00",
  "database": "connected",
  "cv_service": "active"
}
```

**Мелкий вопрос.** В `CLAUDE.md` базовый URL объявлен как
`http://localhost:8000/api/v1`, и `/health` перечислен среди эндпоинтов — то
есть формально это `/api/v1/health`. Но health-чеки принято вешать в корень.
Мы пробуем **сначала `/health`, потом `/api/v1/health`**, так что нам подойдёт
любой. Скажите, какой у вас, — уберём лишнюю попытку.

Поле `cv_service` вы можете заполнять по нашим снапшотам: `active`, если хоть
от одной камеры снапшот моложе `2 × FRAME_INTERVAL` (30 с), иначе `stale`.

## 11. Как это потрогать руками

В репозитории лежит рабочий мок backend, реализующий описанный контракт
целиком — им можно пользоваться как исполняемой спецификацией или
сверять с ним своё поведение.

```bash
cd cv-service
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# поднять мок на 8000
uvicorn tests.mock_backend:app --port 8000

# в другом терминале — валидный снапшот
curl -s -X POST http://localhost:8000/api/v1/internal/occupancy \
  -H "Authorization: Bearer test-cv-token" \
  -H "Content-Type: application/json" \
  -d '{"camera_id":"CAM-001","timestamp":"2026-11-13T10:30:00+10:00",
       "detections":[{"spot_id":"S-014","status":"free","confidence":0.97}]}'

# что мок принял
curl -s http://localhost:8000/__mock__/snapshots

# заставить мок сбоить: mode = 500 | timeout | 401 | ok, remaining = -1 (бесконечно)
curl -s -X POST http://localhost:8000/__mock__/config \
  -H "Content-Type: application/json" -d '{"mode":"500","remaining":3}'

# включить частичный приём: знаем только S-014
curl -s -X POST http://localhost:8000/__mock__/config \
  -H "Content-Type: application/json" -d '{"known_spot_ids":["S-014"]}'
```

Тесты контракта (они же — примеры всех сценариев отказа):

```bash
cd cv-service && python -m pytest tests/test_publish.py -v
```

Файлы:

| Файл | Что внутри |
|---|---|
| `cv-service/cvsvc/publish/schemas.py` | Pydantic v2 модели контракта. EXT-поля помечены комментарием `# EXT` |
| `cv-service/cvsvc/publish/client.py` | Клиент: ретраи, бэкофф, буфер, DLQ, json-логи |
| `cv-service/cvsvc/publish/buffer.py` | SQLite-буфер с упорядочиванием по времени кадра |
| `cv-service/tests/mock_backend.py` | Мок backend — исполняемая спецификация приёмной стороны |
| `cv-service/tests/test_publish.py` | 31 тест: схемы, 401/500/таймаут, дозаливка, границы буфера |
