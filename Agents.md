# Agents.md — Организация AI-агентов для проекта ParkVision

## Общая структура

Проект использует несколько специализированных AI-моделей для разных задач разработки. Каждый агент оптимизирован под конкретный тип работы.

## Роли агентов

### 1. **GPT-6 Astra** — Product & Architecture Lead
**Текущая роль:** Создание спецификаций, архитектурных решений, координация команды

**Зоны ответственности:**
- Написание технических спецификаций и требований
- Архитектурные решения и выбор технологий
- Координация между участниками команды
- Создание пользовательских сценариев и UX-флоу
- Документация проекта

**Когда использовать:**
- Нужно описать новую функцию или модуль
- Требуется принять архитектурное решение
- Необходимо разрешить конфликт между модулями
- Создание документации для команды

### 2. **Codex** (OpenAI) — Backend & API Development
**Зоны ответственности:**
- FastAPI backend разработка
- PostgreSQL/PostGIS схемы и запросы
- REST API endpoints и контракты
- Интеграция с 2ГИС SDK
- Docker Compose конфигурация

**Когда использовать:**
- Разработка backend логики
- Создание API endpoints
- Работа с базой данных
- Настройка окружения и деплоя

**Примеры промптов:**
```
"Создай FastAPI endpoint для получения рекомендаций парковочных мест 
с параметрами user_location, destination, search_mode (closest/fastest)"

"Спроектируй PostgreSQL схему для хранения ParkingSpot с полями: 
id, parking_lot_id, lat, lon, status, confidence, updated_at"
```

### 3. **Opus** (Anthropic Claude) — Code Review & Integration
**Зоны ответственности:**
- Ревью кода всех участников
- Проверка соответствия архитектуре
- Интеграционное тестирование
- Выявление потенциальных проблем
- Рефакторинг и оптимизация

**Когда использовать:**
- Перед merge любого значимого кода
- При интеграции модулей разных участников
- Для анализа производительности
- При возникновении багов

**Примеры промптов:**
```
"Проверь этот FastAPI endpoint на соответствие REST best practices
и безопасность. Особое внимание на валидацию входных данных"

"Проанализируй интеграцию между CV-сервисом и backend API.
Есть ли узкие места или потенциальные race conditions?"
```

### 4. **GLM** (Zhipu AI) — Code Generation & CV Development
**Зоны ответственности:**
- Computer Vision модуль (OpenCV + CNN)
- Flutter мобильное приложение
- Генерация boilerplate кода
- Прототипирование функций
- Административная панель (Streamlit)

**Когда использовать:**
- Быстрое создание прототипов
- Генерация структуры Flutter виджетов
- CV pipeline для обработки кадров
- Создание UI компонентов

**Примеры промптов:**
```
"Создай Flutter Widget для отображения карты с маркерами парковок.
Цвет маркера зависит от количества свободных мест (зелёный/жёлтый/красный/серый)"

"Напиши OpenCV pipeline для обработки ROI парковочных мест:
1. Получить кадр
2. Вырезать ROI
3. Нормализовать
4. Классифицировать (free/occupied/unknown)"
```

## Workflow организации работы

### Фаза 1: Планирование (первые 2 часа)
**Ответственный:** GPT-6 Astra
1. Детализация спецификации для каждого участника
2. Определение API контрактов (JSON схемы)
3. Создание чеклистов задач

### Фаза 2: Параллельная разработка (День 1)
**Участник #1 (CV Engineer):**
- Модель: **GLM** для генерации кода
- Ревью: **Opus** перед коммитом

**Участник #2 (Backend Engineer):**
- Модель: **Codex** для API разработки
- Ревью: **Opus** для проверки архитектуры

**Участник #3 (Flutter Developer):**
- Модель: **GLM** для UI компонентов
- Консультации: **GPT-6 Astra** для UX решений

**Участник #4 (Product/QA):**
- Модель: **GPT-6 Astra** для тестовых сценариев
- Модель: **Opus** для интеграционных тестов

### Фаза 3: Интеграция (День 2, первая половина)
**Ответственный:** Opus
1. Ревью всех модулей
2. Интеграционное тестирование
3. Исправление конфликтов

### Фаза 4: Финализация (День 2, вторая половина)
**Координатор:** GPT-6 Astra
1. Подготовка демо
2. Создание презентации
3. Финальные тесты

## Правила коммуникации между агентами

### Формат запроса к агенту
```markdown
## Для: [Имя агента]
## Контекст: [Краткое описание задачи]
## Входные данные: [Что уже есть]
## Ожидаемый результат: [Что нужно получить]
## Критерии приёмки: [Как проверить]
```

### Формат ответа агента
```markdown
## От: [Имя агента]
## Статус: [Готово/В процессе/Требуется уточнение]
## Результат: [Описание или ссылка на код]
## Замечания: [Предупреждения, ограничения, риски]
## Следующие шаги: [Что делать дальше]
```

## Примеры сценариев взаимодействия

### Сценарий 1: Создание нового API endpoint

```
1. Astra → Codex:
   "Создай endpoint POST /api/v1/recommendations
    Входные данные: user_lat, user_lon, dest_lat, dest_lon, mode
    Выход: список мест с рейтингом"

2. Codex → Результат (код)

3. Opus → Ревью:
   "Проверь endpoint на безопасность, производительность, REST compliance"

4. Opus → Фидбек → Codex исправляет

5. Codex → Astra: "Endpoint готов, обновлена документация API"
```

### Сценарий 2: Разработка Flutter экрана

```
1. Astra → GLM:
   "Создай экран выбора режима поиска с двумя кнопками:
    - 'Ближе к цели'
    - 'Быстрее припарковаться'
    Включи короткие пояснения под кнопками"

2. GLM → Результат (Flutter widget код)

3. Astra → Ревью UX:
   "Проверяю читаемость текста, доступность кнопок, соответствие дизайну"

4. Opus → Ревью кода:
   "Проверяю архитектуру, state management, производительность"

5. GLM → Исправления → Готово
```

### Сценарий 3: Отладка интеграции

```
1. Участник #3 → Opus:
   "Flutter приложение не получает данные от backend API.
    Ошибка: 500 Internal Server Error"

2. Opus → Анализ:
   - Проверяет контракт API
   - Анализирует Flutter код запроса
   - Проверяет backend логи

3. Opus → Codex:
   "В endpoint /api/v1/spots/{id} не обрабатывается случай,
    когда spot не найден. Добавь обработку 404"

4. Codex → Исправление

5. Opus → Участник #3:
   "Проблема решена. Также добавь обработку 404 в Flutter коде"
```

## Мониторинг прогресса

### Ежедневные синхронизации (каждые 4 часа)
**Формат:** Каждый агент/участник отчитывается:
- Что сделано
- Что в процессе
- Что блокирует работу

**Ответственный:** GPT-6 Astra собирает статус и обновляет общий план

### Метрики готовности MVP

| Компонент | Ответственный | Агент | Статус |
|-----------|---------------|-------|--------|
| CV сервис | Участник #1 | GLM → Opus | 🔴 |
| Backend API | Участник #2 | Codex → Opus | 🔴 |
| Flutter UI | Участник #3 | GLM → Opus | 🔴 |
| Интеграция | Участник #4 | Opus → Astra | 🔴 |
| Админка | Участник #4 | GLM | 🔴 |
| Тесты | Участник #4 | Opus | 🔴 |

🔴 Не начато | 🟡 В процессе | 🟢 Готово

## Резервные стратегии

### Если агент недоступен:
- **Codex недоступен** → Использовать GPT-6 Astra для backend
- **GLM недоступен** → Использовать Codex для кодогенерации
- **Opus недоступен** → GPT-6 Astra берёт на себя ревью
- **Astra недоступен** → Opus координирует команду

### Приоритизация при нехватке времени:
1. **P0 (критично):** Базовый сквозной сценарий
2. **P1 (важно):** Два режима поиска работают
3. **P2 (желательно):** Прогноз, админка, полировка UI

## Инструменты коммуникации

### Для 2 человек, пишущих промпты:
- **Человек #1:** Работает с Codex и Opus (backend + ревью)
- **Человек #2:** Работает с GLM и Astra (frontend + координация)

### Шаблоны промптов:
Создать файл `prompts/` с готовыми шаблонами для типовых задач:
- `backend_endpoint.md`
- `flutter_screen.md`
- `cv_pipeline.md`
- `code_review.md`
- `integration_test.md`
